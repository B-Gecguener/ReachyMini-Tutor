## Folie 3: Wichtigste Tätigkeit im Design:
Thema: Die Folie erklärt die Designaufgabe, Zuständigkeiten an Systemteile zuzuweisen, und ordnet diese Tätigkeit in den Designprozess ein.
Inhalt: Die wichtigste Tätigkeit im Design besteht darin, Zuständigkeiten an Systemteile zuweisen. Als Systemteile werden Objekte, Klassen, Pakete und Subsysteme genannt. Der Begriff Zuständigkeit wird als synonym zu Verantwortlichkeit bzw. responsibility erklärt. Wichtig ist, dass das Verteilen von Verantwortlichkeiten in der Regel beim Erstellen von Interaktionsdiagrammen stattfindet, also beispielsweise bei den Umsetzungen von Systemoperationen. Die dort getroffenen Entscheidungen werden dann in Form von Methoden etc. ins Designklassendiagramm übernommen.

## Folie 7: Name:  Experte
Thema: Die Folie stellt das GRASP-Prinzip "Experte" (Expert Pattern) vor und erklärt, nach welchem Grundprinzip eine Zuständigkeit einer Klasse zugewiesen werden soll.
Inhalt: Der Titel der Folie lautet "Das Experte-Pattern", gefolgt vom Untertitel "Experte". Der Name des Prinzips ist "Experte". Das Problem wird formuliert als Frage: Nach welchem Grundprinzip soll eine Zuständigkeit vergeben werden? Die Lösung lautet: Es soll die Klasse zuständig sein, die die relevante Information besitzt. In einem Kasten mit der Überschrift "Mehrere Experten" wird ausgeführt, dass die Information für bestimmte Aufgaben oft auf mehrere Objekte verteilt ist; daraus folgen mehrere Experten für eine Aufgabe, Aufgabenteilung plus Delegation sowie Interaktion mit Nachrichten. In einem zweiten Kasten mit der Überschrift "Analogie" wird eine Analogie zur Realität gezogen: Verantwortlichkeiten werden im Berufsleben meist an die Individuen verteilt, die die nötigen Informationen besitzen; beispielsweise wird eine Gewinn-Verlust-Rechnung vom CFO (Chief Finance Officer) durchgeführt, wobei er wohl auch seine Mitarbeiter um die Erledigung von Teilaufgaben (kursiv) bitten wird.

## Folie 17: Das Erzeuger-Pattern
Thema: Die Folie stellt das GRASP‑Prinzip „Erzeuger" (Creator) als Pattern mit Name, Problem und Lösung sowie einer Liste von fünf Bedingungen dar.
Inhalt: Der Titel lautet „Das Erzeuger‑Pattern". Der Name des Patterns ist „Erzeuger (Creator)". Das Problem wird als Frage formuliert: „Wer soll ein neues Objekt erzeugen?". Die Lösung lautet: Eine Klasse A soll die Verantwortlichkeit zur Erzeugung eines Objekts vom Typ B bekommen, wenn eine der folgenden Bedingungen wahr ist (je mehr desto besser), wobei „eine der folgenden Bedingungen" betont ist. Abschließend steht in Klammern der Hinweis: „(Falls mehr als eine Klasse in Frage kommt, bevorzuge Container bzw. Aggregation)".

## Folie 21: auf andere Klassen  haben?
Thema: Die Folie stellt das GRASP-Prinzip „Schwache Kopplung" (Low Coupling) als Pattern mit Name, Problem, Lösung sowie einer Definition und den negativen Auswirkungen zu starker Kopplung vor.
Inhalt: Der Titel der Folie lautet „Das ‚Schwache Kopplung‘-Pattern". Als Name wird „Schwache Kopplung (Low Coupling)" angegeben. Das Problem wird formuliert als die Frage, wie man sicherstellt, dass Änderungen an einer Klasse wenig Auswirkungen auf andere Klassen haben. Als Lösung wird genannt, Zuständigkeiten so zu verteilen, dass die Kopplung gering bleibt. In einem Kasten mit der Überschrift „Definition" steht, dass Kopplung ein Maß dafür ist, wie stark ein Element (Klasse, Subsystem, etc.) mit anderen Elementen zusammenhängt. In einem zweiten Kasten mit der Überschrift „Zu starke Kopplung" wird ausgeführt, dass zu starke Kopplung oft sehr negative Auswirkungen hat. Im Sinne von GRASP und Designklassen führt dies dazu, dass Änderungen in Klassen meist zu Änderungen in gekoppelten Klassen führen, dass die Klasse für sich allein schwerer verständlich ist und dass Funktionalität nicht unabhängig wiederverwendbar ist. Zusätzlich wird der Aspekt „Im Sinne von Architekturen" als weiterer Punkt genannt.

## Folie 22: A ist an B gekoppelt, wenn …
Thema: Die Folie listet die typischen Formen auf, in denen eine Klasse A an eine Klasse B gekoppelt ist.
Inhalt: A ist an B gekoppelt, wenn A ein Attribut hat, das auf B referenziert (im einfachsten Fall von Typ B ist). A ist an B gekoppelt, wenn A Methoden von B aufruft. A ist an B gekoppelt, wenn A Methoden hat, deren Argumente, Ergebnis oder Implementierung B referenzieren. A ist an B gekoppelt, wenn A eine (direkte oder indirekte) Subklasse von B ist. A ist an B gekoppelt, wenn A ein Interface B implementiert.
Abbildung: Rechts neben jedem Aufzählungspunkt steht ein kleines UML-Klassendiagramm, das die jeweilige Kopplungsform (Attributreferenz, Methodenaufruf, Referenz in Methode, Vererbung, Interface-Implementierung) als Beispiel veranschaulicht.

## Folie 23: Was bedeutet Kopplung = 0?
Thema: Die Folie thematisiert die Probleme, die mit dem Konzept der Kopplung verbunden sind, und warnt davor, "schwache Kopplung" isoliert zu betrachten.
Inhalt: Die Folie stellt zunächst die Frage, was eine Kopplung gleich null bedeutet, und antwortet, dass dies keine Beziehungen und dadurch keine Kommunikation zwischen Klassen bedeutet. Anschließend wird gefragt, wie man immer eine Kopplung gleich null erzielen kann, mit der Antwort, dass man eine einzige, allumfassende Klasse verwenden würde, was als Antipattern "Gottklasse" bezeichnet wird. Abschließend wird ausgeführt, dass "schwache Kopplung" ein Prinzip ist, das nicht isoliert betrachtet werden kann.
Abbildung: Ein UML-Klassendiagramm, das eine einzelne Klasse darstellt und als Beispielbild für eine allumfassende Klasse dient.

## Folie 46: Konsequenz aus dem OCP: Kapselung
Thema: Die Folie erklärt die Kapselung als Konsequenz aus dem Open/Closed Principle im objekt-orientierten Design.
Inhalt: Kapselung ist ein zentraler Bestandteil objekt-orientierten Designs und Programmierens. Kapselung meint das Verstecken der internen Repräsentation eines Objekts vor Objekten anderer Klassen. Als Konvention gilt, dass alle Felder einer Klasse K privat sein sollten. Alle Klassen (außer K) sind dadurch abgeschlossen gegenüber Änderungen der Felder. ## Folie 56: Zusammenfassung SOLID
Thema: Die Folie ist eine Zusammenfassungsfolie, die die fünf SOLID-Prinzipien der objektorientierten Softwareentwicklung mit je einer kurzen Definition auflistet.
Inhalt: Die Folie trägt den Titel „Zusammenfassung SOLID" und führt die fünf Prinzipien in folgender Reihenfolge auf. Beim Single Responsibility Principle (SRP) heißt es: Es soll nie mehr als einen Grund geben, eine Klasse zu ändern. Beim Open/Closed Principle (OCP) heißt es: Klassen sollten offen sein gegenüber Erweiterungen, aber abgeschlossen gegenüber Modifikationen. Beim Liskov Substitution Principle (LSP) heißt es: Subtypen müssen sich so verhalten wie ihre Basistypen. Beim Interface Segregation Principle (ISP) heißt es: Klassen sollten nicht gezwungen werden von Interfaces abzuhängen, die sie nicht benutzen. Beim Dependency Inversion Principle (DIP) heißt es: High-Level Module sollten nicht von Low-Level Modulen abhängen, beide sollten von Abstraktionen abhängen.
